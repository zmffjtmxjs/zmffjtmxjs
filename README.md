## 검증까지 설계한 워크플로우로 AI와 일하는 백엔드 개발자

만드는 일과 그것이 맞는지 판정하는 일을 나눠서 합니다. 생성과 1차 검증은 AI에 맡기고,
무엇을 확인할지와 통과 기준은 제가 정합니다.

관심은 데이터가 어긋나지 않는 쪽에 있습니다 — 동시에 들어온 요청이 같은 자원을 건드릴 때
무엇이 깨지는지를 재현해 보고, 고친 뒤에 다시 재서 확인합니다.

부산IT교육센터 풀스택 과정 수료 예정(2026.09) · Java / Spring Boot / JPA / MySQL

### AI와 일하는 방식

맡긴 결과는 변경된 내용을 따로 확인한 뒤 반영합니다. 에이전트의 1차 검증과 제 diff 확인을
병렬로 두고, **최종 판단과 머지는 제가 쥡니다.**

반대 방향으로도 씁니다 — 직접 타이핑한 코드를 같은 리뷰에 걸어 **두 라운드에 걸쳐 결함 9건**이
나왔습니다. 개별 로직은 옳은데 줄과 줄 사이의 관계가 틀린 것들이었습니다. 정식 코드 리뷰가
도는 환경이 아니어서, 리뷰어가 없는 자리를 장치로 대신한 것입니다.

한 번은 에이전트가 **확정되지 않은 자기 제안을 이미 결정된 사양인 것처럼 인용**했습니다.
그대로 따랐다면 하지 않기로 한 설계가 코드에 들어갈 뻔했습니다. 정답을 알려주는 대신
그 기준이 무엇이었는지를 되물었고, 그것만으로 잘못된 전제가 걷혔습니다.
같은 결의 착오가 그날 세 번 있었고 세 번 다 같은 방식으로 걸렀습니다.

경계는 다짐이 아니라 장치로 둡니다. 팀 프로젝트(LifeQuest)에서는 **파일 편집·커밋·push
세 지점**에 Claude Code 훅을 걸어 두었습니다.

### 주로 다뤄본 문제

- **동시 요청과 정합성**(LifeQuest) — 완료 요청이 겹쳐도 결과는 1건이고 양쪽 모두 정상 응답해야
  한다는 계약을 먼저 고정하고, 중복 판정을 애플리케이션이 아니라 DB UNIQUE 제약에 맡겼습니다.
  1차 캐시가 잠금을 무력화해 경험치가 유실되던 것을 **기댓값 80 대비 실제 30**으로 재현해
  확정하고, 수정 후 **100**을 확인했습니다.
  ([PR #12](https://github.com/mahoora0/LifeQuest/pull/12) — 결함 내용과 검증 범위를 본문에 남겼습니다)
- **격리 수준과 락** — 락을 걸기 전에 실행된 일반 조회가 읽는 시점을 먼저 고정해,
  락을 얻은 뒤의 존재 확인까지 과거를 보는 것을 두 세션으로 재현해 확인했습니다.
  **격리 수준과 구현을 바꿨습니다.** 재현 스크립트를 남겨 같은 절차로 다시 확인할 수 있게 했습니다.
- **트랜잭션 경계** — 외부 API 호출이 트랜잭션 안에 있어 응답을 기다리는 동안 DB 커넥션을
  붙잡던 구조를, 전파 속성을 나눠 외부 호출만 밖으로 옮겼습니다.
- **테스트가 통과해도 남는 결함** — 계약 테스트 10건이 전부 초록불인데 배정 API의 동시 요청
  5건 중 4건이 500이었습니다. 요청을 하나씩 보내는 테스트로는 안 잡히던 것이라,
  진단 테스트로 눈에 보이게 한 뒤 예외를 잡는 위치를 트랜잭션 밖으로 옮겼습니다.
  배정에 성공한 1건과 밀린 4건이 **모두 정상 응답**을 받습니다 — 밀린 쪽은 500이 아니라
  이미 배정됐다는 결과를 돌려받습니다. 진단 테스트 자체는 AI가 작성했고 저는 그 결과로 판정했습니다.
